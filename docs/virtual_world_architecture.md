## 1. System Overview & Core Principles

This specification defines the architecture for extending the `canary_ssm` statistical research codebase into a **Virtual Data Center** simulator and interactive monitoring platform. The system models a physical fleet of server racks, simulated workloads, multi-metric telemetry streams, infrastructure faults, and versioned canary releases. A hierarchical state-space detector provides early, statistically rigorous detection and attribution of release degradations versus shared infrastructure shifts.

### 1.1 Core Architectural Principles

1. **Numerical Simulation First:**  
   The primary engine is a discrete-time numerical simulation. A simulated memory leak models process memory state accumulation ($\Delta \text{mem}_t$); resource pressure functions dictate if and when latency increases or error rates spike. 
2. **Artifact Upload $\ne$ Execution:**  
   Code uploads are stored as versioned release artifacts in an artifact registry and tagged with declared simulation behavior profiles. The UI and API must explicitly label uploaded source files as *unexecuted artifacts*. Simulated telemetry is generated by numerical simulation of declared behavior profiles, *never* from arbitrary host execution of uploaded code. (Actual sandboxed code execution is reserved for an optional separate testbed stage).
3. **Strict Separation of Detector Input vs. Hidden Truth:**  
   The simulator produces typed `TelemetryObservation` streams and permitted deployment metadata (`rollout_id`, `host_id`, `class_id`, `exposed`, `timestamp`). Detector modules (`factor`, `preprocess`, `kalman`, `hierarchy`, `decision`) and UI dashboards consume *only* observed telemetry. Hidden truth (`Truth`, fault schedules, injected magnitudes, affected sets) is strictly confined to the `FaultLab` developer view and `Evaluator` metrics. The browser and detector never read fault labels for inference.
4. **Working Increments Roadmap:**  
   Implementation proceeds strictly in working increments:
   $$\text{WORLD FIRST} \longrightarrow \text{TELEMETRY \& FAULTS} \longrightarrow \text{DEPLOYMENT \& DASHBOARD} \longrightarrow \text{HIERARCHICAL SSM} \longrightarrow \text{VALIDATION}$$
   Existing test suites, CLI entry points, and pipelines remain fully working and runnable after every increment.

## 2. Two Distinct Hierarchies

A central requirement of the virtual data center is maintaining a strict conceptual, mathematical, and algorithmic distinction between two orthogonal hierarchies: the **Physical Infrastructure Hierarchy** and the **Release Effect Hierarchy**.

```
+--------------------------------------------------------------------------------+
|                             PHYSICAL HIERARCHY                                 |
|                                                                                |
|    Fleet (Shared Workload x_t, Fleet-wide Common Factor f_t)                   |
|      │                                                                         |
|      ├── Rack 1 (Rack Nuisance Shift gamma_1, Top-of-Rack Switch, Power/Net)   |
|      │     ├── Server 1 [Baseline Control]                                     |
|      │     ├── Server 2 [Baseline Control]                                     |
|      │     └── Server 3 [Canary Host]                                          |
|      └── Rack 2 (Rack Nuisance Shift gamma_2)                                  |
|            ├── Server 4 [Baseline Control]                                     |
|            └── Server 5 [Canary Host]                                          |
+--------------------------------------------------------------------------------+
                                       ▲
                                       │ (Cross-product / Identifiability Guard)
                                       ▼
+--------------------------------------------------------------------------------+
|                          RELEASE EFFECT HIERARCHY                              |
|                                                                                |
|    Release Artifact (Version tag, Behavior Profile, Commit/Checksum)           |
|      │                                                                         |
|      └── Compatibility Group g in G (Hardware / Service Architecture Class)    |
|            │   (Class Effect: theta_g ~ N(0, sd_g^2))                          |
|            │                                                                   |
|            └── Canary Server i (Host Deviation: b_i ~ N(0, sd_h^2))            |
|                  Total Canary Effect: a_it = theta_{g(i), t} + b_{it}          |
+--------------------------------------------------------------------------------+
```

### 2.1 Physical Hierarchy (Nuisance & Infrastructure Variation)
$$\text{Fleet} \longrightarrow \text{Rack} \longrightarrow \text{Server}$$
- **Fleet:** Represents the entire physical datacenter cluster. Experiences diurnal and exogenous traffic shocks ($x_t$), shared capacity limits, and cluster-wide common factor fluctuations ($f_t$).
- **Rack:** A physical enclosure of servers sharing power distribution, cooling, and a Top-of-Rack (ToR) network switch. Racks experience local physical faults: ToR switch packet loss, port congestion, link flaps, and localized power throttling ($\gamma_j(t)$).
- **Server:** A physical host with CPU, memory, network interfaces, and disk. Exhibits individual baseline efficiency ($\mu_i$), workload elasticity ($\beta_i$), and idiosyncratic temporal autoregressive noise ($e_{it}$).

### 2.2 Release Effect Hierarchy (Software Regression Variation)
$$\text{Release} \longrightarrow \text{Compatibility Group} \longrightarrow \text{Canary Server}$$
- **Release:** The versioned software build or configuration bundle being evaluated.
- **Compatibility Group ($g \in \mathcal{G}$):** Predeclared, immutable hardware or service class attributes (e.g., `arm64` vs. `x86_64`, kernel version, or microservice instance sizing). Group effect $\theta_g(t)$ captures shared regressions specific to that class.
- **Canary Server ($i \in \text{Canary}$):** An individual server assigned to run the candidate release. Local deviation $b_i(t)$ captures host-specific regression variation (e.g. state-dependent memory leak rate or cache-dependent slowdown).

### 2.3 Identifiability Contract & The Identifiability Trap

> [!WARNING]
> **The Identifiability Trap:** If rack identity is conflated with compatibility group or canary allocation—for instance, if an entire rack is assigned only canary servers—a rack switch fault and a release regression become mathematically indistinguishable:
> $$r_{it} = \gamma_j(t) + a_{it} \implies \text{observationally identical when } \forall i \in \text{Rack } j, \text{exposed}_i = 1.$$

**Mathematical Guard Rules:**
1. **Coexistence Requirement:** Within every represented rack $j$ and every represented compatibility group $g$, both canary servers and baseline control servers must coexist:
   $$\forall j \in \text{Racks}_{\text{active}}, \quad |\text{Canaries}_j| \ge 1 \quad \text{and} \quad |\text{Controls}_j| \ge 1$$
   $$\forall g \in \text{Groups}_{\text{active}}, \quad |\text{Canaries}_g| \ge 1 \quad \text{and} \quad |\text{Controls}_g| \ge 1$$
2. **Estimation Separation:**
   - **Same-rack baseline controls** estimate rack variation $\gamma_j(t)$.
   - **Cross-rack baseline controls** estimate fleet variation $f_t$ and workload response $\beta_i x_t$.
3. **Allocation Gatekeeper:** The deployment coordinator must inspect candidate canary allocations. If any rack or compatibility group lacks sufficient controls (default: minimum 1 same-rack control, ideally $\ge 3$), the deployment is either:
   - **Blocked at dry-run:** Refusing the allocation with an explanatory diagnostic.
   - **Flagged at runtime:** Setting advisory status to `INSUFFICIENT ATTRIBUTION / DATA` and withholding causal regression alarms.

## 3. Observation & Telemetry Decomposition

For any server $i$ in rack $j$ belonging to compatibility group $g$ at discrete simulated minute $t$, multi-metric telemetry observation vector $\mathbf{y}_{it} \in \mathbb{R}^M$ is decomposed as follows:

$$\mathbf{y}_{ijt} = \boldsymbol{\mu}_i + \boldsymbol{\beta}_i x_t + \boldsymbol{\lambda}_i f_t + \boldsymbol{\gamma}_j(t) + \mathbb{I}(i \in \text{Canary}) \cdot \mathbf{a}_{it} + \mathbf{e}_{it} + \boldsymbol{\nu}_{it}$$

### 3.1 Telemetry Metric Channels & Formal Units

| Metric Key | Name | Raw Unit | Modeled Form | Typical Healthy Baseline | Fault Manifestation |
|---|---|---|---|---|---|
| `workload` | Normalized Traffic Pressure | dimensionless ($x_t$) | Log-workload $x_t \sim \text{AR}(1)$ | Mean $0.0$, SD $0.03$ | Diurnal cycle, step shifts |
| `latency_ms` | Request Latency | milliseconds ($\text{ms}$) | $y_{it} = \log(\text{latency\_ms})$ | $100.0 \text{ ms}$ ($\mu_i \approx \log 100$) | Algorithmic regression, resource saturation |
| `memory_mb` | Process Resident Set Size | Megabytes ($\text{MB}$) | Level $M_{it} \in [0, M_{\text{cap}}]$ | $4096 \text{ MB} \pm 200 \text{ MB}$ | Gradual leak rate $\Delta M / \Delta t > 0$ |
| `cpu_pct` | Host CPU Utilization | percentage ($\%$) | Level $C_{it} \in [0, 100]\%$ | $35\% \pm 5\%$ | Workload scaling, GC spin, spinlocks |
| `errors` | Failed Request Count | count / minute | Rate or discrete count | $0 \text{ to } 2 \text{ errors/min}$ | Service 5xx, timeout drops |
| `request_volume`| Served Request Volume | requests / minute | Count $V_{it} \in \mathbb{N}$ | $6000 \text{ req/min}$ | Traffic shedding, connection throttling |

### 3.2 Resource Pressure Coupling Model

Degradations across channels do not jump instantaneously; they follow realistic physical resource coupling:
1. **Modeled Memory Dynamics:**
   $$M_{it} = M_{\text{base}, i} + \beta_{\text{mem}} x_t + \mathbb{I}(\text{leak active}) \cdot \sum_{\tau=t_{\text{leak}}}^t \delta_{\text{leak}}(\tau) + \epsilon_{\text{mem}, it}$$
2. **Coupling to Latency & CPU:**
   - **Normal Zone ($M_{it} < 0.70 \cdot M_{\text{cap}}$):** Latency is dictated purely by workload elasticity and latency effects: $y_{it} = \mu_i + \beta_i x_t + \lambda_i f_t + \gamma_j(t) + a_{\text{lat}, it} + e_{it}$.
   - **Pressure Zone ($0.70 \cdot M_{\text{cap}} \le M_{it} < 0.90 \cdot M_{\text{cap}}$):** Garbage collection activity increases CPU utilization $C_{it} \mathrel{+}= 15\% \times \frac{M_{it} - 0.7 M_{\text{cap}}}{0.2 M_{\text{cap}}}$, and minor latency jitter appears.
   - **Thrashing / OOM Zone ($M_{it} \ge 0.90 \cdot M_{\text{cap}}$):** Paging and heavy GC trigger exponential latency expansion $y_{it} \mathrel{+}= \kappa_{\text{page}} (M_{it} - 0.9 M_{\text{cap}})$, and error rate jumps due to OOM kills or dropped connections.

## 4. Hierarchical State-Space Model (SSM) Strategy

The detector architecture maintains mathematical rigor across univariate and multivariate stages:

```
[Telemetry Stream] 
       │
       ▼
[Workload & Fleet Factor Adjustment] (factor.py: OLS + rank-1 SVD on controls)
       │
       ▼
[Rack Nuisance Adjustment] (Same-rack control contrasts: gamma_hat_j(t))
       │
       ▼
[Adjusted Canary Residuals r_it]
       │
       ├── Channel 1: Latency SSM (hierarchy.py: Kalman Filter on C*theta + B*b)
       └── Channel 2: Memory Growth Channel (Validated linear drift filter)
               │
               ▼
   [Multi-Channel Policy Fusion] (Joint ECDF order-statistic calibration)
```

1. **Step 1: Adjusted Latency Channel (Core SSM):**  
   Pre-period OLS workload slope adjustment $\beta_i x_t$, rank-1 fleet common factor projection $\lambda_i \hat{f}_t$, and same-rack control baseline subtraction $\hat{\gamma}_j(t)$. Kalman filter estimates class regression $\theta_g(t)$ and host deviation $b_i(t)$.
2. **Step 2: Memory Growth Channel:**  
   Separate validated sequential drift detector monitoring $\Delta M_{it}$ against pre-period empirical variance.
3. **Multi-Channel vs. Multivariate Policy Distinction:**  
   - Two univariate channels evaluated under a Boolean union rule ($\text{Alarm} = \text{Alarm}_{\text{latency}} \lor \text{Alarm}_{\text{memory}}$) form a **Multi-Channel Detector**. They must undergo **Joint Calibration** (max-statistic across null runs) to prevent doubling the false-alert budget.
   - The detector will only be designated **Jointly Multivariate** once cross-metric covariance matrices $\mathbf{\Sigma}_{LM}$ or coupled state-transition dynamics $\mathbf{F}_{LM}$ are formally estimated.

## 5. Record Schemas & Data Contracts

All entities are typed versioned dataclasses. Identifiers are stable alphanumeric strings. Timestamps are integer indices $t \in \mathbb{N}_{\ge 0}$ representing discrete 1-minute intervals.

```python
@dataclass(frozen=True)
class ServerConfig:
    server_id: str             # e.g., "srv-r01-01"
    rack_id: str               # e.g., "rack-01"
    class_id: int              # Compatibility group (0: x86_standard, 1: arm64_highmem)
    base_latency_ms: float     # Nominal latency mu_i
    memory_capacity_mb: float  # e.g., 16384.0 MB
    base_cpu_pct: float        # e.g., 25.0%

@dataclass(frozen=True)
class RackConfig:
    rack_id: str               # e.g., "rack-01"
    switch_id: str             # e.g., "tor-sw-01"
    server_ids: tuple[str, ...]

@dataclass(frozen=True)
class FleetConfig:
    fleet_id: str              # e.g., "fleet-primary"
    racks: tuple[RackConfig, ...]
    servers: dict[str, ServerConfig]

@dataclass(frozen=True)
class TelemetryRecord:
    timestamp: int             # Event time t (discrete minute)
    server_id: str
    rack_id: str
    class_id: int
    version_id: str            # "v1.0.0-baseline" or "v1.1.0-canary"
    is_canary: bool
    latency_ms: float
    memory_mb: float
    cpu_pct: float
    errors: int
    request_volume: int
    workload: float            # Cluster-level measured workload x_t
    observed: bool             # Record emitted
    arrival_time: int          # Arrival at decision engine (timestamp + delay)

@dataclass(frozen=True)
class ReleaseArtifact:
    release_id: str            # e.g., "rel-2026-11-01"
    version_tag: str           # e.g., "v1.2.0-canary"
    checksum_sha256: str
    artifact_filename: str     # e.g., "canary_worker_v120.py"
    is_executed: bool          # MUST BE FALSE for numerical simulation
    declared_behavior: dict    # e.g., {"memory_leak": {"rate_mb_min": 15.0, "affected_canaries": 2}}

@dataclass(frozen=True)
class FaultDefinition:
    fault_id: str
    target_scope: str          # "rack" | "server" | "fleet"
    target_id: str             # rack_id or server_id
    fault_type: str            # "tor_packet_drop" | "memory_leak" | "cpu_hog"
    onset_time: int            # t_onset
    duration: int              # minutes
    severity: float            # magnitude
    seed: int
```

## 6. System Boundaries & Repository Mapping

Responsibilities are organized into modular domains within the existing `canary_ssm` repository:

| Domain | Target Path | Responsibility | Boundary & Access Controls |
|---|---|---|---|
| **world** | `canary_ssm/world/` | Fleet, Rack, Server topology; deterministic seeded clock; event scheduler | Emits ground truth state to simulator; no detector imports |
| **workloads** | `canary_ssm/workloads/` | Diurnal cycle generator, host elasticity $\beta_i$, capacity curves | Driven by clock; receives no detector feedback |
| **faults** | `canary_ssm/faults/` | Explicit fault definitions, seeded scheduling, developer fault lab | Truth stays here; strictly isolated from detector endpoints |
| **telemetry** | `canary_ssm/telemetry/` | Typed observations, late arrivals, missingness, telemetry buffers | Provides read-only observation views to detector & API |
| **deployments** | `canary_ssm/deployments/` | Versioned release registry, artifact metadata, exposure allocations | Validates allocation coexistence rules before exposure |
| **detectors** | `canary_ssm/` (existing) | OLS adjustment, Kalman filter, hierarchical SSM, baselines, oracles | Reads only `TelemetryObservation`; NEVER imports truth |
| **policy** | `canary_ssm/policy/` | Eligibility gating, calibrated thresholds, dual advisory state | Computes `InfrastructureAdvisory` and `CanaryAdvisory` |
| **api** | `canary_ssm/api/` | REST/SSE endpoints for world clock, deployment actions, telemetry | Serves frontend; hides truth unless requested by FaultLab |
| **dashboard** | `canary_ssm/dashboard/` | 5-page UI (World, Releases, Fault Lab, Monitoring, Evaluation) | HTML5/CSS3/JS single-page application served via API |
| **evaluation** | `canary_ssm/evaluation/` | Replay runner, ground truth comparison, ROC/PR, report generation | Evaluator only; compares frozen detector outputs to truth |

## 7. Concrete First Demo Specification

### 7.1 Demo World Configuration
- **Topology:** 4 racks (`rack-01` .. `rack-04`), 6 servers per rack = 24 servers total.
- **Hardware Classes:** 2 compatibility groups (Group 0: 3 servers/rack; Group 1: 3 servers/rack).
- **Pre-exposure baseline:** 180 simulated one-minute intervals ($t \in [0, 180)$).
- **Canary Allocation:** Exactly 1 canary server per rack (4 canaries total), leaving 5 baseline controls per rack (20 controls total). Canaries span both compatibility groups (2 in Group 0, 2 in Group 1).
- **Post-exposure monitoring:** 120 simulated one-minute intervals ($t \in [180, 300)$).
- **Benchmark configuration:** The full 100-host, 10-canary benchmark is retained as `configs/plain_main.yaml` / `configs/default.yaml`.

### 7.2 Three Acceptance Scenarios

1. **Scenario A: Canary Memory Leak**  
   - Release deployed to the 4 canaries at $t=180$.
   - Configured memory leak injected on 2 canaries ($+25 \text{ MB/min}$).
   - Modeled memory grows linearly. Latency remains flat initially, rising only when memory reaches pressure thresholds.
   - **Expected Evidence:** Canary-specific memory drift detected; latency detector triggers upon pressure; rack controls remain healthy; `Canary Release Advisory` transitions to `PAUSE RECOMMENDED`.
2. **Scenario B: Rack Network Slowdown (Shared Fault)**  
   - ToR switch packet loss injected on `rack-02` at $t=200$, affecting all 6 servers in that rack (1 canary + 5 controls).
   - **Expected Evidence:** Same-rack controls show matching latency rise; rack nuisance estimate $\hat{\gamma}_2(t)$ absorbs the shift; canary residual $r_{it}$ remains zero; `Infrastructure Advisory` marks `rack-02 DEGRADED`; `Canary Release Advisory` remains `RUNNING`.
3. **Scenario C: Compound Fault & Identifiability Stress**  
   - Network slowdown on `rack-02` combined with release memory leak on canaries. If a test allocation places only canaries on `rack-02`, the system detects non-identifiability and outputs `Advisory: INSUFFICIENT ATTRIBUTION / DATA`.

## 8. Dashboard Architecture & Dual Advisory States

### 8.1 Five Dashboard Pages

1. **World View:** Rack cards containing server tiles. Live status indicators for version (`v1.0.0` vs `v1.1.0`), CPU/memory bars, latency sparkles, data freshness, and simulation controls (Start, Pause, Step 1m, Reset, Speed $1\times/10\times/60\times$).
2. **Releases:** Artifact upload interface (with explicit label: *"Uploaded artifact stored for simulation profiling; code is not executed"*), declared behavior profiles, canary server picker with dry-run identifiability check, deploy action, and simulated rollback button.
3. **Fault Lab:** Developer view for manual and random fault injection (rack network drop, host memory leak, CPU spike, packet loss, missing telemetry). Truth is inspectable here only.
4. **Monitoring:** Real-time multi-metric plots (Latency, Memory, CPU, Errors) comparing canaries against baseline controls. Displays hierarchical class effects $\theta_g$, host deviations $b_i$, release scores, calibrated thresholds, and eligibility reasons.
5. **Evaluation:** Historical replay, ground truth comparison, time-to-detection vs. false alarm tables, ROC curves, and downloadable CSV summaries.

### 8.2 Dual Independent Advisory States

The dashboard maintains two separate advisory streams to prevent confusing infrastructure outages with release bugs:

```
[System Health State]
   │
   ├── Infrastructure Advisory:
   │     • NORMAL: All racks operating within nominal baseline parameters.
   │     • RACK_DEGRADED: One or more racks experiencing ToR switch or localized infrastructure degradation.
   │     • FLEET_OUTAGE: Cluster-wide common factor shock or severe external workload surge.
   │
   └── Canary Release Advisory:
         • RUNNING: Canary residuals within calibrated null threshold.
         • PAUSE RECOMMENDED: Attributable canary regression exceeds calibrated threshold (FAR <= 0.05).
         • ROLLED BACK: Operator or automated action halted canary deployment.
         • INSUFFICIENT DATA / UNCERTAIN: High missingness or missing control hosts prevent statistical attribution.
```

An operator can manually trigger Deploy, Pause, or Rollback at any time; detector recommendations remain purely advisory.

## 9. Framework Selection & Technology Stack

To adhere strictly to repository instructions ("Reuse working code. Identify current frontend/backend frameworks and reuse them. Do not install a second framework just to follow proposed module names"):

1. **Language & Numerical Stack:** Python 3.10+ with existing `numpy`, `scipy`, `pandas`, `pyyaml`, `matplotlib`, `statsmodels`, `pytest`.
2. **Backend API:** Built-in Python standard library `http.server` or `fastapi` + `uvicorn` (already installed in local environment). Clean JSON REST endpoints and Server-Sent Events (SSE) for 1Hz telemetry streaming.
3. **Frontend Dashboard:** Lightweight, zero-build HTML5/CSS3/JavaScript SPA served directly by the backend. Avoids NodeJS/npm dependencies and build steps, ensuring seamless, deterministic execution on any Windows/Linux host.
